# 远程推送（Remote Push Notification）

远程推送是现代移动应用与用户建立高效连接的重要机制。它允许服务器主动将消息发送至用户设备，实现提醒、更新、召回等功能，而无需用户主动打开 App。

本章节旨在为 **Notification Service Extension（NSE）** 的介绍做铺垫，对远程推送的核心机制进行简要说明。如需更深入的配置和实现细节，建议参考 Apple 官方文档或第三方推送服务的完整教程。

> 🧭 后续可以补充完整推送配置与实战细节，或欢迎有经验的开发者补充。



## 一、远程推送的基本工作流程

1. **服务器准备推送内容**
   根据业务逻辑，服务器构造推送 payload，通常包含标题（`title`）、正文（`body`）、声音（`sound`）、角标（`badge`）等字段，亦可附带自定义数据（如业务 ID、图片地址等）。
2. **发送推送请求到 APNs**
   推送服务端通过 HTTP/2 接口，将构造好的 payload 发给 Apple 推送服务器（APNs）。
3. **APNs 分发通知到设备**
   Apple 推送服务验证请求后，将通知路由到目标设备。
4. **设备收到并展示通知**
   系统收到通知，根据 payload 展示本地通知 UI，或交由 App 拓展进一步处理（如 NSE）。



## 二、远程推送的调试

### 使用命令行发送模拟推送

> 只能在模拟器中使用

#### 1.创建文件并打开

```
touch test.apns
open -e test.apns
```

#### 2.填充推送内容

```
{
  "aps": {
    "alert": {
      "title": "测试标题",
      "body": "这是通过 Simulate Remote Notification 测试的内容"
    },
    "mutable-content": 1,
    "sound": "default"
  },
  "image-url": "https://via.placeholder.com/300x150.png"
}
```

`mutable-content: 1` 是**必须的字段**，告诉系统触发 NSE

附加字段如 `image-url` 可自定义，供你在 NSE 中解析使用



#### 3. 执行发布命令

```
xcrun simctl push booted "bundleId" "apnsFilePath"
```

示例

```
xcrun simctl push booted org.cocoapods.demo.McccNotify-Example /Users/Mccc/Desktop/apns.apns
```

## 四、远程推送的内容限制与挑战

远程推送虽然是移动应用中非常重要的功能，但在实际应用中存在以下几个主要限制和挑战：

### 1. Payload 大小受限

- APNs 对单条推送通知的 payload 大小有限制，通常不能超过 4KB。
- 这意味着通知中的文本内容、附件信息和自定义数据都必须精简，无法直接包含大容量的富媒体内容。

### 2. 内容静态缺乏灵活性

- 推送的内容大多由服务器预先生成，固定不变。
- 这种静态内容无法根据用户的当前状态、设备环境或上下文进行动态调整，限制了个性化推送的实现。

### 3. 富媒体支持有限

- 虽然推送可以携带附件字段，但图片、音频、视频等富媒体无法直接内嵌在推送中。
- 需要额外下载处理，增加了实现的复杂度，同时也影响了推送的展示效果和用户体验。

### 4. 安全与隐私风险

- 推送通知中可能包含敏感信息或业务数据。
- 网络传输和存储过程中存在被窃取或篡改的风险。
- 如何保障用户隐私和数据安全，是推送系统设计必须重点考虑的问题。

------

这些限制使得传统远程推送在丰富通知内容和提供个性化体验方面存在一定的瓶颈。为了克服这些不足，Apple 提供了新的机制和扩展方案，帮助开发者提升推送的表现力和灵活性。





## 五、Notification Service Extension

为了解决传统远程推送的内容固定、缺乏个性化、富媒体处理复杂等问题，Apple 提供了 Notification Service Extension（NSE）机制。

它允许 App 在系统准备展示推送通知前，对通知内容进行二次处理，包括：

- 动态修改标题、正文、声音
- 插入图片、音频、视频等富媒体
- 执行解密操作
- 替换关键内容

我们将在下一章节深入介绍 Notification Service Extension 的功能、结构与使用场景。





## 六、DeviceToken 

### token **会重新分配（改变）的时机**

1. **App 卸载后再重装**
   - 卸载操作会让旧 token 在 APNs 端标记为 `Unregistered`。
   - 重装后调用 `registerForRemoteNotifications()`，系统会返回一个新的 token。
2. **用户在同一设备上清除所有设置 / 恢复出厂设置**
   - 设备标识重置，token 也会变化。
3. **用户更换设备（迁移/换新手机）**
   - 每个设备生成的 token 不同，迁移到新设备时，必须重新请求 token。
4. **应用签名/Bundle ID 发生变化**
   - token 绑定的是 **App ID（包含 TeamID+BundleID）**。
   - 改签名、切换到不同的 BundleID/环境（Debug→Release）都会拿到新的 token。
5. **系统升级 / 网络栈调整 / Apple 内部策略更新**
   - Apple 文档说明：系统有权 **在任意时刻重新分配 token**，原因可能是内部安全策略或基础设施迁移。
   - 所以即便用户和设备环境没变，也可能突然获得新 token。
6. **用户退出 iCloud / 更换 Apple ID**
   - 某些场景下 APNs token 会跟着 Apple ID 环境变化而刷新。

**token 不是永久不变的，它可能因为卸载/重装、换机、BundleID/签名变化、系统更新、Apple 策略而被重新分配。**
所以客户端要 **周期性上报**，服务端要 **根据 APNs 响应做清理**。





### 什么是 token，什么叫“失效”

- **APNs 设备 token**：由系统分配，**按设备 × App BundleID × 环境（Sandbox/Production）** 唯一。
- **“失效/不可用”的几种含义**
  1. **APNs 层面失效**：对该 token 发推送会返回错误（如 `Unregistered`/`BadDeviceToken`）。
  2. **业务层面失效**：服务器保存的是**旧 token**，或绑定关系错了（例如用户换机/重装后没及时上报新 token）。
  3. **可用但不展示**：用户关闭通知权限、系统策略拦截等——**token 本身没问题**，只是看起来“到不了”。



### 如何发现 token 已失效（服务端）

- **按错误码分流处理**（HTTP/2 APNs 响应）：
  - `410 Unregistered`：立即**标记并删除**该 token，记录时间戳；等待客户端重新上报。
  - `400 BadDeviceToken`/`DeviceTokenNotForTopic`：检查**环境/Topic/签名**是否一致。
  - `200` 但端上未展示：属于**非 token 问题**，应走端上可见性日志与权限/场景排查。
- **失败率看板**：分原因维度（环境不匹配、未注册、鉴权失败、限频/拥塞等）做漏斗。



### 何时刷新/更新 token（客户端“更新时机”设计）

> 目标：**提高有效 token 覆盖率**，避免服务器持有旧 token。

**推荐的刷新时机（全部落地即可）：**

1. **每次冷启动 / 回到前台**：调用 `registerForRemoteNotifications()`，获取最新 token；若与本地缓存不同，**上报服务器 upsert**。
2. **通知权限变更**：从 `UNAuthorizationStatus` 的回调/前后台切换时检测变化，**重新注册并上报**。
3. **用户登录/登出**：更新**账号 ↔ token** 绑定关系（1:N 设备）。
4. **App 升级/重签/切环境**：版本或签名信息变化后，**强制触发重新上报**。
5. **服务端返回 410/400 后**：对该用户（或设备标识）在**下次会话**强制拉起重新注册逻辑。
6. **容错性周期刷新**：如**7～14 天**做一次保底刷新，覆盖“系统随机更新 token”的长尾。





### 通过 local push 补偿 token 失效用户进行刷新后仍未到达的用户

**核心难点就是：App 客户端怎么知道“这条远程推送用户没收到”？**

------

#### 一、为什么不能直接知道

- **APNs 不会给客户端回执**（不会告诉设备“我推过一条，你收没收”）。
- 客户端也没办法直接监听“远程通知是否送达通知栏”。

所以需要 **服务端 + 客户端 协同设计**，才能推断“没收到”。

------

#### 二、常见检测思路

### 1. **服务端投递日志对比**（最常见）

- 服务端每次发 push，都会写一条记录（msgId + userId + 时间）。
- 客户端埋点：当 App **被推送唤醒** 或 **用户点击通知进入** 时，上报 `msgId`。
- 服务端比对：哪些消息**下发了但客户端没有回执** = 可能没送达。
- 客户端下次启动/刷新时，拉取这些“漏达消息”，再用 **local push** 触发。

👉 实现要点：**消息必须有唯一 ID**，且要有 **服务端存储 & 客户端确认机制**。

------

#### 2. **Pull 拉取补偿**

- App 启动/刷新数据时，调用服务端接口：
  “请给我最近 N 分钟内，我应该收到但没确认的通知”。
- 服务端根据 **投递日志 - 客户端已确认** 的差集，返回漏掉的消息。
- 客户端收到后，决定是否通过 **local push** 弹出。
